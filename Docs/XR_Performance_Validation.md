# Windows PCVR 性能验证

## 本轮优化范围

- Review V2：按状态复用会话快照；后台串行写盘及读回，改变设计前仍需匹配保存回执；异步准备下一套设计，只有主线程通过碰撞验证才替换原设计。首次加载、实际激活和碰撞同步仍有主线程成本。
- 反馈界面：先按当前会话／方案筛选再复制记录，复用已有看板行和世界标记，不强制刷新所有 Canvas。
- 画质：没有保存过画质偏好的 Windows Player 默认 Performance（关闭屏幕空间反射和 AO）；Editor 默认 Standard，已保存的选择不变。未更改 URP/HDRP 管线类型、分辨率策略或 Android 设置。
- 物理：保留 XR 持物 Transform 同步和完整碰撞规则；无候选时不改写穿透探针。水流仅优化视觉轨迹，真实水量、容器和碰撞积分不变。
- 网格：关闭桌子两档、近档餐椅和近档吊灯的 CPU 可读副本；保留碰撞和编辑流程所需网格。

## 本机验证记录（2026-11-19）

Unity 2022.3.62f3 定向 EditMode **48/48**；定向 PlayMode **26/26**，覆盖真实 V2 标记提交、锁文件失败及重试、归属与切换、回顾行复用、占用回滚、安全退出、持物、水量、画质和家具通行。较宽的 PlayMode 批次用于基线比较：原分支 `f4c442c` 有 23 项失败；优化初次跑同一范围时这 23 项也失败，另外暴露一项异步切换下的持物位置精度断言，已在定向批次复测通过。部分原失败与旧 UI 入口和测试夹具中重复方向光有关；未将不同范围的测试拼成全量通过。Quest Link 实际帧率和显存对照未执行。

## Quest 3 + Quest Link 同条件对照

1. 使用 **Unity 2022.3.62f3 / StandaloneWindows64**，同一源码分别生成默认 Cooking Player 和通过 `ReviewV2Authoring.BuildValidation` 生成 Review V2。不要切换构建平台。采样窗口不使用 Deep Profile。
2. 固定 Windows PC、OpenXR/Quest Link 运行时、刷新率、每眼渲染尺寸及 Link 设置。以 `-kitchen-quality performance`、`-kitchen-quality standard` 分别启动同一个 Player；参数只覆盖本次启动，不写入 PlayerPrefs。不把镜像窗口的 FPS 当作头显帧率。
3. 预热后重复固定路线：静立转头；双手持物靠近柜体并贴边转动；开水、接水、倾倒；V2 提交标记并查看列表、A/B 往返、结束读回。反馈用隔离目录，并另测长历史。记录异常（重投影、掉帧、无效追踪）、CPU 主线程、GPU 帧时间和 `GC Alloc` 的 P95/P99，以及保存和切换过程中最长帧。
4. 以实际头显刷新率核算单帧间隔，例如 90 Hz 约 11.1 ms。分别比较空闲和交互尖峰；同时查看视觉差异、双手保持和接触、倒水表现，以及切换失败能否保留当前世界。编辑器回归与局部采样不能替代设备数据。
